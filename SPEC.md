# Промпт для Claude Code: параметрический генератор горшков (web UI)

> Скопируй этот файл в корень пустого репозитория как `SPEC.md`, положи рядом
> референсную реализацию `potgen.py`, и запусти Claude Code с задачей:
> «Прочитай SPEC.md и реализуй проект целиком согласно спецификации.
> Начни с плана, потом реализуй по этапам из раздела "Порядок работ".»

---

## 1. Что строим

Одностраничное веб-приложение — параметрический конструктор квадратных
рассадных горшков под печать в режиме вазы (spiral vase) на FDM-принтере.
Пользователь крутит параметры, видит модель в 3D в реальном времени, видит
рассчитанные метрики (объём субстрата, граммы филамента, время печати),
получает предупреждения о непечатаемых сочетаниях параметров и скачивает STL.

Целевой пользователь — один человек, который печатает горшки под саженцы
розмарина на Bambu Lab P2S, PETG. Приложение локальное, без бэкенда,
без аккаунтов, без сети.

**Референс:** `potgen.py` в корне репозитория — рабочая реализация геометрии на
Python. Вся математика оттуда переносится в TypeScript **без изменения
алгоритма**. Это не «вдохновиться», это порт с проверкой эквивалентности
(см. раздел 8, golden-тесты).

## 2. Стек

- **Vite + React 18 + TypeScript** (strict mode, `noUncheckedIndexedAccess`)
- **three.js** + `@react-three/fiber` + `@react-three/drei` (OrbitControls, Grid, Environment)
- **zustand** — состояние параметров (persist в localStorage)
- **Tailwind CSS** — вёрстка
- **vitest** — тесты
- Никакого бэкенда. Вся геометрия считается в браузере, STL собирается
  в `ArrayBuffer` и отдаётся через `Blob` + `URL.createObjectURL`.
- Тяжёлую генерацию меша вынести в **Web Worker**, чтобы UI не фризился при
  высоком разрешении сетки. Обмен через transferable `ArrayBuffer`.

Язык: **код, идентификаторы и inline-комментарии — английский. UI и
документация — русский.**

## 2.1 Изоляция окружения — обязательно

**Всё реализуется и запускается изолированно, только в Docker-контейнерах.
Локальная отладка — тоже исключительно в контейнерах.** На хост-машине не
устанавливается ничего: ни Node, ни pnpm, ни Python, ни зависимостей. Хост
предоставляет только Docker и Docker Compose.

Требования:

1. **`Dockerfile`** — multi-stage:
   - `base` — Node 22 (`node:22-bookworm-slim`), включённый corepack, pnpm
     фиксированной версии.
   - `deps` — установка зависимостей по `pnpm-lock.yaml` c
     `--frozen-lockfile`, кэш pnpm-store через `RUN --mount=type=cache`.
   - `dev` — окружение для `pnpm dev` и тестов.
   - `build` — `pnpm build`, статика в `/app/dist`.
   - `runtime` — `nginx:alpine` со статикой из `build`, для проверки
     production-сборки.
2. **`Dockerfile.python`** — отдельный образ (`python:3.12-slim`) для
   референсного `potgen.py` и скрипта генерации golden-фикстур. Питон на
   хосте не нужен и не предполагается.
3. **`docker-compose.yml`** — сервисы:
   - `dev` — Vite dev-server, порт `5173:5173`, `--host 0.0.0.0` (иначе снаружи
     контейнера не достучаться), bind-mount исходников для HMR, **анонимный
     volume на `/app/node_modules`**, чтобы хостовая папка не затирала
     установленные в образе зависимости.
   - `test` — `pnpm test` / `pnpm test:watch`.
   - `lint` — `tsc --noEmit`, eslint, `pnpm docs:check`.
   - `build` — production-сборка, `dist/` наружу через bind-mount.
   - `preview` — nginx с собранной статикой, порт `8080:80`.
   - `fixtures` — образ из `Dockerfile.python`, гоняет `potgen.py` и
     перегенерирует `tests/fixtures/*.json`.
4. **`.dockerignore`** — как минимум `node_modules`, `dist`, `.git`,
   `.idea`, `*.stl`.
5. **`Makefile`** (или `./run.sh`) — тонкая обёртка над compose, чтобы
   единственные команды, которые человек набирает на хосте, были вида:
   `make dev`, `make test`, `make lint`, `make build`, `make preview`,
   `make fixtures`, `make shell`. Прямых вызовов `pnpm` на хосте в
   документации быть не должно.
6. **Отладка в контейнере:**
   - Node-отладчик в `dev`-сервисе: `--inspect=0.0.0.0:9229`, порт наружу,
     конфиг «Attach to Docker» для VS Code/WebStorm — описать в
     `docs/development.md`.
   - Vite HMR обязан работать через bind-mount; если файловые события не
     долетают (частый случай на macOS/Windows), включить
     `server.watch.usePolling`.
   - Логи тестов и сборки — в stdout контейнера, без записи артефактов на
     хост мимо примонтированных путей.
7. **Пользователь в контейнере — не root** (`node`, uid 1000), иначе файлы,
   созданные в bind-mount (`dist/`, фикстуры), приходят на хост с правами
   root.
8. **CI прогоняет ровно те же compose-сервисы**, что и локальная разработка.
   Никаких отдельных «CI-only» шагов, ставящих Node напрямую: расхождение
   сред между CI и локалью недопустимо.

Критерий изоляции: на чистой машине с одним лишь установленным Docker
последовательность `git clone && make dev` поднимает работающее приложение,
а `make test` — зелёные тесты.

## 3. Геометрия (переносится из potgen.py)

### 3.1 Базовое сечение

Скруглённый квадрат через суперэллипс:

```
x = a · sign(cos t) · |cos t|^(2/k)
y = a · sign(sin t) · |sin t|^(2/k)
k = max(2.5, 2a / corner_r)
```

Плотная выборка (720 точек), затем **ресемплинг по длине дуги** до `SEG`
точек. Ресемплинг обязателен: без него точки кучкуются в углах и гофр
получается неравномерным.

### 3.2 Гофр (fluting)

Смещение каждой точки вдоль внешней нормали:

```
d(s) = flute_amp · cos(2π · flutes · s),   s = j / SEG
```

Нормаль считается по центральной разности соседних точек контура.
`flutes` кратно 4 — сохраняется четырёхкратная симметрия, углы попадают
на гребень волны.

**Зачем гофр:** в режиме вазы стенка = одна нитка экструзии. Гладкий квадрат
мнётся пальцами. Синусоида по периметру — единственный способ добавить
жёсткости, не разрывая непрерывный контур. Это ключевая идея модели,
не выпиливать.

### 3.3 Профиль по высоте

- Линейный конус `bottom_size → top_size`. **Зачем:** горшки вкладываются
  друг в друга при хранении и перевозке.
- `corner_r` и `flute_amp` масштабируются пропорционально текущему полуразмеру
  сечения — иначе вложение перекашивает.
- **Развальцовка кромки:** на последних `rim_h` мм контур раздувается наружу
  на `rim_flare · g²`, где `g` — нормализованная позиция внутри зоны кромки.
  **Зачем:** упор при вложении (иначе горшки заклинивает намертво) плюс
  жёсткость верха.
- `twist` (град/мм) — опционально, по умолчанию 0. Кручение ломает вложение,
  UI должен об этом предупреждать при `twist != 0`.

### 3.4 Меш

Замкнутый манифолд: боковая поверхность + нижняя крышка (веер) + верхняя
крышка (веер). Слайсер в режиме вазы обводит внешний контур, внутренность
и верх игнорирует. Обход граней — CCW при взгляде сверху, нормали наружу.

## 4. Параметры

| Параметр | Тип | Дефолт (P9) | Диапазон | Описание |
|---|---|---|---|---|
| `topSize` | мм | 90 | 40–200 | внешняя ширина по кромке |
| `bottomSize` | мм | 68 | 30–190 | внешняя ширина по дну |
| `height` | мм | 95 | 40–250 | высота |
| `cornerR` | мм | 10 | 2–40 | радиус угла по кромке |
| `flutes` | шт | 32 | 0–80, шаг 4 | число волн гофра, 0 = гладко |
| `fluteAmp` | мм | 1.1 | 0–4 | амплитуда гофра |
| `rimH` | мм | 6 | 0–20 | высота развальцованной кромки |
| `rimFlare` | мм | 1.3 | 0–5 | вылет кромки наружу |
| `twist` | °/мм | 0 | −2…2 | кручение |
| `seg` | шт | 256 | 64–1024 | точек на сечение |
| `dz` | мм | 0.5 | 0.2–2 | шаг по высоте |

Настройки печати (влияют только на расчёт метрик и на режим shell):

| Параметр | Дефолт | Описание |
|---|---|---|
| `nozzle` | 0.4 | диаметр сопла |
| `wallWidth` | 0.75 | ширина экструзии = толщина стенки в режиме вазы |
| `layerH` | 0.28 | высота слоя |
| `bottomLayers` | 4 | сплошных слоёв дна |
| `density` | 1.27 | г/см³ (PETG) |
| `speed` | 70 | мм/с, эффективная скорость для оценки времени |

## 5. Расчётные метрики (панель справа, обновляется вживую)

- **Полезный объём, л** — интегрирование площади сечения, ужатого на одну
  толщину стенки, до уровня «12 мм ниже кромки».
- **Масса филамента, г** — объём стенки (периметр × wallWidth × dz,
  просуммированный) + дно (площадь × bottomLayers × layerH), × плотность.
- **Стоимость** — граммы × цена за грамм (поле ввода, дефолт 1.5 ₽/г).
- **Слоёв** — height / layerH.
- **Время печати, мин** — слои × средний периметр / speed. Пометить
  «грубая оценка, сверяться со слайсером».
- **Шаг вложения, мм** — насколько вырастает стопка при добавлении горшка.
  Считать реально: опустить копию модели по Z до первого контакта
  (по огибающей радиуса сечения), а не по формуле конуса. Показывать
  «сколько штук влезет в 250 мм».
- **Угол стенки от вертикали, °** — для контроля свеса.

## 6. Валидация и предупреждения

Отдельный блок в UI, каждое правило — с текстом причины:

| Условие | Уровень | Текст |
|---|---|---|
| период гофра < 3 мм | error | сопло не отработает волну, получится каша |
| `fluteAmp` > период/3 | warning | слишком крутая волна, будут артефакты |
| `wallWidth` > `nozzle × 1.8` | error | недостижимая ширина экструзии |
| `wallWidth` < `nozzle` | warning | стенка тоньше сопла, продавливание |
| угол стенки > 45° | warning | свес, в режиме вазы поедет |
| `bottomSize` > `topSize` | error | обратный конус, вложение невозможно |
| `twist` ≠ 0 | info | вложение работать не будет |
| `cornerR` > `bottomSize / 2` | error | углы схлопываются |
| `bottomLayers × layerH` < 0.8 | warning | PETG протечёт по дну |
| `seg × (height/dz)` > 500k вершин | warning | тяжёлый STL, тормоза |

Плюс постоянно висящая **памятка ограничений режима вазы**:
1. Дренажные отверстия в режиме вазы **не сделать** — контур непрерывный.
   Горячий гвоздь 4 мм, 4 отверстия после печати.
2. Bambu Studio / PrusaSlicer не дают spiral vase больше чем на один объект
   на столе. Партии печатаются последовательно.

## 7. Функциональность UI

**Раскладка:** слева панель параметров (сворачиваемые группы: Форма / Гофр /
Кромка / Печать), по центру 3D-вид, справа метрики + предупреждения.

1. **3D-превью** — orbit controls, сетка стола, тумблер матовый/каркас,
   тумблер «показать разрез по XZ».
2. **2D-виды** — вкладка с двумя графиками (canvas или SVG):
   сечение сверху (кромка и дно наложены) и профиль сбоку. Как в
   `preview.png` из референса.
3. **Пресеты** — встроенные `P9 90×90×95` и `Small 78×78×82`, плюс
   пользовательские (localStorage), импорт/экспорт JSON.
4. **Шаринг** — все параметры кодируются в URL hash, ссылка восстанавливает
   состояние.
5. **Экспорт STL** — binary, имя файла генерируется из параметров
   (`pot_90x90x95_f32.stl`). Прогресс-бар при генерации в воркере.
6. **Панель настроек слайсера** — генерирует текстовую сводку рекомендуемых
   настроек под текущие параметры, с кнопкой «копировать»:
   spiral vase on, line width, layer height, bottom layers, сопло 245–250 °C,
   обдув 30–40 % (одностенка держится на межслойной адгезии, сильный обдув
   её убивает), скорость, брим не нужен.
7. **Overlay дренажа** — на 2D-виде дна показать 4 точки, куда бить отверстия.
8. **Undo/redo** по изменениям параметров.

### 7.1 Режим Shell (второй режим генерации)

Тумблер `mode: 'vase' | 'shell'`.

В режиме `shell` генерируется настоящая тонкостенная модель:
внешняя поверхность + внутренняя (смещённая внутрь на `wallThickness`) + дно
заданной толщины + **настоящие дренажные отверстия** (число и диаметр —
параметры) + опциональные вертикальные щели для воздушной обрезки корней.

**Зачем:** режим вазы даёт один горшок за печать. Shell-модель печатается
2 стенками с нулевым заполнением, зато 9 штук за раз на столе. Для партии в
сотню это принципиальная разница. Метрики и предупреждения должны
пересчитываться под этот режим.

## 8. Тесты (vitest)

- **Golden-тесты порта.** Для обоих пресетов сравнить с эталоном из
  `potgen.py`: число треугольников, bounding box, объём меша (через
  дивергенцию), площадь поверхности. Допуск 1e-6 относительный.
  Эталонные значения зафиксировать в `tests/fixtures/*.json`, положить
  туда же скрипт, которым они сгенерены. Скрипт запускается **только** в
  питоновском контейнере (`make fixtures`), версия Python и зависимости
  зафиксированы в `Dockerfile.python` — иначе эталон плывёт между машинами.
- **Манифольдность:** каждое ребро принадлежит ровно двум треугольникам,
  ориентации согласованы. Проверить на 20 случайных наборах параметров.
- **Нормали наружу:** объём по дивергенции строго положителен.
- **Ресемплинг:** после ресемплинга разброс длин сегментов < 1 %.
- **Симметрия:** при `flutes % 4 == 0` и `twist == 0` сечение инвариантно
  к повороту на 90°.
- **Валидатор:** таблица из раздела 6 покрыта тестами построчно.
- **Парсер STL:** записанный файл читается обратно и даёт исходные вершины.

## 9. Документация — обязательный блок

Документация не «README на десять строк». Требуется следующее, целиком:

### `README.md`
Что это, скриншот, быстрый старт (`make dev` — и ничего кроме Docker на хосте),
сборка, требования к среде, лицензия, ссылки на остальные документы.
Команд `pnpm` для запуска на хосте в README быть не должно.

### `docs/development.md`
Работа в контейнерах: устройство `Dockerfile` и `docker-compose.yml`,
все цели `Makefile`, как поднять dev-сервер и почему `--host 0.0.0.0`,
как работает HMR через bind-mount и что делать, если он молчит (polling),
подключение отладчика к `9229` из VS Code и WebStorm, запуск тестов и
отладка тестов в контейнере, перегенерация golden-фикстур через
питоновский образ, права на файлы и non-root пользователь, чистка
volume-ов и кэшей.

### `docs/geometry.md`
Полный разбор математики: суперэллипс и вывод показателя `k`, ресемплинг по
длине дуги и зачем он нужен, расчёт нормалей, формула гофра, масштабирование
радиуса угла и амплитуды по высоте, квадратичный профиль развальцовки,
триангуляция и правило обхода. Каждая формула — в LaTeX-блоке. К каждому
параметру — SVG-иллюстрация, что он меняет (генерируются скриптом
`scripts/gen-docs-figures.ts`, не рисуются руками).

### `docs/printing.md`
Полное руководство по печати: почему режим вазы, почему PETG, температуры,
обдув и его связь с межслойной адгезией на одностенке, выбор сопла
(0.4 vs 0.6) и вытекающая толщина стенки, настройки Bambu Studio по пунктам,
ограничение «один объект на столе», дренаж горячим гвоздём, режим shell как
альтернатива для партий, оценка себестоимости и времени, вложение и хранение,
поведение PETG на улице и на солнце.

### `docs/architecture.md`
Схема модулей и поток данных (параметры → воркер → меш → three.js / метрики /
валидатор → UI). Почему геометрия в воркере. Почему нет бэкенда. Границы
модулей: `core/` не знает про React, `ui/` не знает про three.js напрямую.
Диаграмма — Mermaid.

### `docs/api.md`
Справочник публичного API `core/`: сигнатуры, типы, инварианты, примеры
вызова. Каждая экспортируемая функция описана. Генерируется из TSDoc через
TypeDoc, но с ручным вводным разделом.

### `docs/extending.md`
Как добавить новый тип сечения (шестигранник, овал), новое правило валидации,
новый формат экспорта (3MF, OBJ). С рабочими примерами кода.

### `docs/decisions.md`
ADR-записи по ключевым решениям: порт на TS вместо FastAPI, суперэллипс вместо
скругления фасками, гофр как способ жёсткости, манифолд-солид вместо
тонкостенной модели для режима вазы, два режима генерации.

### Требования к качеству документации
- **TSDoc на каждом экспорте** из `core/`, с `@param`, `@returns`,
  `@example`, `@throws`.
- Inline-комментарии объясняют **почему**, а не что. `// resample by arc
  length: uniform angular sampling clusters points at corners and makes the
  fluting uneven` — хорошо. `// loop over points` — мусор, не писать.
- Все примеры кода в документации должны компилироваться. Добавить
  `pnpm docs:check`, который извлекает блоки кода из markdown и прогоняет
  через `tsc --noEmit`. Завести это в CI-скрипт.
- Таблица параметров в `README.md` **генерируется** из определения схемы
  параметров, а не дублируется руками. Рассинхрон недопустим.

## 11. Порядок работ

**Этап 0 — контейнерное окружение из раздела 2.1**: `Dockerfile`,
`Dockerfile.python`, `docker-compose.yml`, `Makefile`, `.dockerignore`.
Это первый этап, а не последний: весь дальнейший код пишется и запускается
уже внутри контейнеров. `make dev` должен подниматься на пустом каркасе Vite.

1. Каркас проекта, `core/params.ts` со схемой и пресетами.
2. `core/profile.ts` + `core/mesh.ts` + `core/stl.ts`, golden-тесты против
   `potgen.py`. **Без зелёных golden-тестов дальше не идти.**
3. `core/metrics.ts`, `core/validate.ts` + тесты.
4. Воркер, минимальный UI, 3D-превью, экспорт STL.
5. Панель метрик, предупреждения, подсказки слайсера.
6. 2D-виды, пресеты, URL-шаринг, undo/redo.
7. Режим shell.
8. Документация целиком, генерация фигур, `docs:check`.

Коммиты по этапам, осмысленные сообщения.

## 13. Критерии приёмки

- На хосте установлен **только Docker**. `make dev` поднимает приложение
  в контейнере (доступно на `http://localhost:5173`), крутилки меняют модель
  без заметной задержки на дефолтном разрешении сетки, HMR работает.
- Ни один шаг разработки, тестирования, сборки и отладки не требует
  установки Node, pnpm или Python на хост.
- Экспортированный STL из пресета `P9` побайтово эквивалентен по геометрии
  выводу `potgen.py` (в пределах float32).
- STL открывается в Bambu Studio, режим вазы включается без ошибок,
  предпросмотр даёт одну непрерывную спираль.
- `make test` и `make lint` зелёные (тесты, `tsc --noEmit`, `docs:check`),
  прогнанные в контейнерах; CI использует те же compose-сервисы.
- `make build` + `make preview` отдают рабочую production-сборку через nginx.
- Документация из раздела 9 присутствует полностью, без заглушек
  и без «TODO».
